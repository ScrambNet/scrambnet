# ScrambNet 规范 —— 第 10 部分：可复现构建与供应链

> **非规范性翻译。** 规范版本以英文为准（[en](../../en/spec/10-reproducible-build.md)）。

**状态：草稿（DRAFT）。** 本部分决定一方如何在 I-3——没有权威——之下，*不去信任
构建它的任何人*就获得一个它能信任的 ScrambNet **二进制文件**，面对的是一个其贡献者
皆为**化名**、因而不带任何用户可核验之身份的项目。它是第 8 部分的软件类比：那里，
一份*映射*之所以受信任，是因为它从公开输入重建得出；而这里，一个*二进制文件*之所以
受信任，是因为它从公开源码重建得出。被标记为 `(s)` 的是 strawman 值。

第 9 部分说的是*节点代码必须做什么*；本部分说的是*那段代码如何变成一个你能核验
自己正在运行的二进制文件*。先读 §1 与 §10：二者合起来说明了本部分买到了什么
（以复现、而非签名，作为裁决者），又承认了它买不到什么（忠实复现的源码里的后门；
一个可复现地错误编译的编译器；以及，对于无法重建的用户，一次向 OP-2 的归约——
与第 8 部分收尾时相同的那次归约）。

本部分决定以可复现性作为信任**锚**。它**并不**决定*谁签署一个发布，以及签名者如何
被选定与替换*——那是条目 4.1（OP-8），另属一部分。二者之间的接缝是 §9，它经由引用
对应到第 8 部分的 ID-11/ID-11a。

## 1. 这一决定，用两句话

- **没有发布权威。** 一个 ScrambNet 二进制文件是一个**可复现、内容寻址的产物
  （artifact）**，任何一方都能从打了标签的公开源码与被钉定的公开输入逐字节地将其
  重建；两方认同一个二进制文件是诚实的，不是因为某个受信任方签了名，而是因为它们
  算出了**相同的 `BLAKE2s`**（RB-1、RB-9）。一个由固定签名者集合册封的二进制文件
  就是换了名字的发布权威，而 I-3 禁止它。
- **一致由复现达成；签名只*定位*一个构建，它们绝不*授权*它；对一个用户自身无法复现
  的构建的信任，归约为按数量佐证，即 OP-2。** 这是那个诚实的形态，并且它被摆在前面
  陈述，而非埋藏起来：对一个拥有构建机器的方而言，复现扛起全部信任；对一台无法重建
  的手机——那个模态（modal）用户——而言，信任系于一个独立复现者数目的计数，恰如
  第 8 部分里不重建的客户端系于一个被 gossip 的法定人数（RB-7b、§10）。

所以那个诚实的结局与第 8 部分就映射所达到的结局是同一个：**自己复现它，信任便是
无权威的；无法复现它，你就回到一个受 OP-2 约束的佐证法定人数。** 以下的一切都是把
「自己复现它，并检测出任何撒谎者」具象化，而 §10 是任何构造都无法消除的残余。

## 2. 范围，以及本部分所要规避的陷阱

一个化名项目无法要求用户去信任它的作者——没有作者可供信任。最省事的「无信任」设计
是一个由项目维护者签名的二进制文件；那恰恰重新偷运回 I-3 所否定的那个权威。陷阱
在于：一个能用受信任密钥悄悄发出恶意二进制文件的签名者，正是条目 4.1 存在所要避免
的那个总开关（kill switch）。所以信任绝不能经由*谁签了名*流动；它经由*它是否重建
得出*流动。

- **RB-1（没有发布权威；复现是裁决者）。「[规范性]」** 获取或校验一个构建的任何
  一步都不得（MUST）要求信任某个特定的方编译、签名或册封了它。唯一受信任的操作是
  (a) 重新计算 `BLAKE2s`，以及 (b) 从打了标签的源码与被钉定的输入重建该产物并
  比对。任何无法被一个执行 (a) 或 (b) 的不受信任替代物所取代的设计要素，依据 I-3
  即为缺陷，且必须（MUST）被移除或在 §10 中声明。（操作 (b)，即重建并比对，是
  **以工具链残余为模**受信任的：运行构建会执行那个被钉定的编译器，而 RB-3b 将其
  声明为一个「trusting-trust」残余——重建把信任归约到编译器，它并不消除编译器。
  RB-1 是那条两操作声称，须连同那个交叉引用一并读，而非脱离它。）
- **RB-2（可复现性授权；签名只定位）。「[规范性]」** 本部分对*谁签署一个发布，以及
  签名者如何被选定与替换*不作任何决定——那是条目 4.1。一个针对某个构建的签名，倘若
  它存在的话，必须（MUST）被当作一个**定位符**（「一个带着此 `H_build` 的构建曾在
  此处、于此时、由这只化名之手被公告」），绝不被当作一个**授权**（「这就是要运行的
  那个构建」）。一个合规的客户端不得（MUST NOT）*因为*一个构建被签了名就采纳它；
  *要采纳哪个*构建是条目 4.1 的关切，且是客户端本地的、选择加入的。把构建诚实性
  绑定到一个签名者集合，会重新偷运回 I-3 禁止的那个权威（ID-11a 规则，用于软件）。
- **RB-2a（共用工具，而非共用权威）。** 本部分可以（MAY）重用第 8 部分的透明性日志
  构造（ID-6）与 GR-6 gossip 通道去发布并 gossip 构建哈希（RB-14）——共用*机制*
  不费分毫（ID-11a）。它不得（MUST NOT）与映射共用一组方——**签名者或日志追加者
  名册**——其角色对映射与代码二者都是承重的，因为那组方会是 I-3 禁止的那个总开关，
  如今还能同时扳动地理推断与软件。那个共用的日志不引入任何权威，**因为**两部分都
  把信任经由复现、而非经由日志来路由，并且该日志保持无需许可（ID-7）。

## 3. 工具链，按内容钉定

- **RB-3（工具链按内容钉定，而非按通道名钉定）。「[规范性]」** 构建必须（MUST）
  钉定一个*确切的*工具链——一个特定的稳定版发布（strawman：`rust-toolchain.toml`
  里的 `rust 1.xx.y`，带 `channel = "1.xx.y"`，绝不用 `stable`/`latest`/`beta`/
  `nightly`）——**并且**在构建清单（manifest）中以 `BLAKE2s` 钉定该工具链的二进制
  产物（RB-8）。「工具链」是一组被哈希的字节，而非某个镜像可以作出不同解析的名字。
  一个重建者从**任意**镜像取回工具链并核验那些哈希（I-3：分发者可替换；字节已钉定
  ——ID-3 模式应用于编译器）。
- **RB-3a（钉定整个编译面）。** 该钉定必须（MUST）覆盖其输出抵达产物的每一个工具：
  `rustc`、`cargo`、实际链接进去的 `std`/`core` 预构建库、链接器（strawman：一个
  被钉定的 `lld`/`mold`（s），而非宿主环境里的 `ld`）、libc/sysroot，以及任何一个
  `build.rs` 所调用的工具。一个留给宿主环境的工具就是一个未钉定输入，也是一处确定性
  隐患（RB-6、RB-18）。
- **RB-3b（编译器是一个被取回的二进制文件——「trusting-trust」是一个已声明的
  残余）。「[规范性]」** 那个被钉定的 `rustc` 是一个*被取回的二进制文件*，而非这条
  流水线从源码构建出来之物。信任它是一个**已声明的残余**（§10，「trusting-trust」）：
  RB-3 钉定*哪些*编译器字节被所有人使用，所以所有重建者共享*同一个*残余，并且任何
  *替换*都因背离而可检测；它并**不**使那个编译器变得诚实。钉定证明的是**来源
  （provenance）**，而非**诚实（honesty）**（见 RB-18）。一条从源码自举（bootstrap）
  或多样化双重编译（diverse-double-compilation）的路径，倘若有朝一日被采纳，是作为
  未来工作被点名的，而非此处所要求的。

## 4. 密封（hermetic）构建

构建是一个**从清单到一个逐字节相同产物的纯函数**。确定性就是整场游戏的全部：如果
两个诚实构建者可能产生背离，哈希相等（RB-9）便不再意味着「同一个二进制文件」，诚实
构建者会被标记成一次攻击（RB-7、RB-15）——这是第 8 部分的教训（ID-4 前言），在此
若未学到便会是致命的。

```
  构建是清单（RB-8）的一个纯函数

  ┌──────────────────────── manifest (RB-8) ────────────────────────┐
  │  source commit/tag · toolchain hashes (RB-3) · every dependency  │
  │  content hash (RB-5) · fixed environment (RB-4b) · target triple │
  │  · SOURCE_DATE_EPOCH (derived, RB-4b) · expected H_build         │
  └────────────────────────────┬────────────────────────────────────┘
                               ▼
            ┌─────────────────────────────────────────┐
            │  HERMETIC BUILD (pure fn, RB-4)          │
            │  no network (RB-4a), no ambient host     │
            │  state, fixed env (RB-4b), nondeterminism │
            │  eliminated per the pinned hazard set    │
            │  (RB-6, versioned by toolchain)          │
            └───────────────────┬─────────────────────┘
                               ▼
                    artifact (for ONE target triple)
                               │
                               ▼
              H_build = BLAKE2s(artifact)   ← the build's ONLY name (RB-6a)
                                              defined per (source, manifest,
                                              target triple) — RB-6b

  Alice ─ same manifest, same triple ─▶ H_A     Two honest builders agree by
  Bob   ─ same manifest, same triple ─▶ H_B     equal H_build. Reproduction is
                                                 the arbiter (RB-7), not a signer.
```

- **RB-4（密封、离线、无环境污染的构建）。「[规范性]」** 构建必须（MUST）在**无网络
  访问**且**无宿主环境残留状态**的情况下运行：不读取 `$HOME`、宿主环境变量（超出一个
  显式允许名单之外，RB-4b）、用于任何嵌入值的系统时钟、用户/组名、主机名、会影响
  输出之处的 CPU 数目，或沙箱之外的任何路径。合规的基底（substrate）有：一个
  Nix/`crane` 风格的纯派生（derivation），**或**一个移除了网络命名空间并带固定最小
  环境的容器/`bwrap` 沙箱。本部分指定的是那些**性质**，并不强制任一基底（I-1：一个
  敌意实现者能从这些性质构建出一个合规的构建器）；Nix 与一个被沙箱化的容器被点名为
  那两个参考性合规基底。一个采纳某基底的方也必须（MUST）把*它*钉定（一个 Nix 工具链
  本身就是一处 RB-3 钉定）。
- **RB-4a（绝不进行构建期网络取回）。「[规范性]」** 构建不得（MUST NOT）取回任何
  东西——没有注册表（registry）访问，没有 git 依赖解析，没有 `build.rs` 下载，没有
  工具链拉取。每一次取回都发生在密封步骤*之前*，按哈希钉定，并经由清单递入。一个
  *能够*触及网络的构建即便恰好没有用到它也是不合规的，因为它的确定性那时就依赖于一台
  服务器（ID-4c 的禁止浮动输入条款，用于软件）。
- **RB-4b（固定、声明、派生的环境）。「[规范性]」** 构建环境必须（MUST）被固定在、
  且只被固定在清单里：locale `C`/`C.UTF-8`、`TZ=UTC`、umask、env 允许名单，以及
  `SOURCE_DATE_EPOCH`。`SOURCE_DATE_EPOCH` 必须（MUST）**从打了标签的提交确定性地
  派生得出**（被钉定标签的提交者日期），从而它是一个被钉定输入的函数，而非一个
  构建者可随意设定的、自由浮动的清单断言。一个伪造的提交者日期不是一次悄无声息的
  得手：它改变 `H_build`，因此被背离逮到（RB-7），恰如任何其他输入改动一样。

## 5. 依赖树

- **RB-5（最小化、经审计、已 vendored、按内容钉定的依赖树）。「[规范性]」** 依赖
  必须（MUST）是 (a) *最小化的*——每一个都要相对于「不要它」被辩护，因为每个 crate
  都是信任链条里一个不受信任的作者（RB-16、OP-10）；(b) *已 vendored 的*——每一个
  传递依赖的确切源码都被钉定进构建输入，而非实时解析（RB-4a）；以及 (c) *按内容
  钉定的*——`Cargo.lock` 已提交，**并且**每个 crate 还额外以其源码的 `BLAKE2s` 在
  清单中被钉定（RB-8），而不是单单信任注册表自己的校验和。一个能在一个名字下改变
  字节的注册表就是一个权威；内容哈希移除了它，并把注册表变成一个可替换的 CDN。
- **RB-5a（锁文件是必要的，而非充分的）。** `Cargo.lock` 钉定版本与注册表校验和；
  它本身并不使*构建*可复现（特性统一（feature unification）、`cfg`、宿主差异仍会
  咬人——RB-6），也不移除对注册表的信任。RB-5 的内容钉定与 RB-4 的密封性弥合了那个
  缺口。一个只钉定了锁文件的构建是不合规的。
- **RB-5b（构建脚本与 proc-macro 是受信任的计算，而非惰性数据）。「[规范性]」**
  `build.rs` 脚本与过程宏（procedural macro）*在构建期*执行任意代码；它们必须
  （MUST）在 RB-4 沙箱内、依同样的无网络/无环境污染规则运行，并且它们完全如同运行期
  代码一样在 RB-16 审计的范围之内。一个读取时钟或网络的 proc-macro 是一处确定性隐患
  与一处供应链面，二者合一。

## 6. 确定性隐患，以及构建如何将其钉定

下述每一项隐患都是一个两名诚实构建者可能产出不同字节之处。构建过程必须（MUST）消除
每一项；不这样做的构建是不合规的，因为它无法支撑 RB-9，而它的背离会被 RB-7 误读
成一次攻击。

- **RB-6（隐患集合是规范性的，按工具链版本化）。「[规范性]」** 构建必须（MUST）消除
  所用工具链版本的**被钉定隐患集合**里的每一项隐患。这个集合是「截至某个被钉定工具链
  为规范性的」，而非永远（残余 §10.7：面对工具链流变，确定性是一个移动的靶子），并且
  清单必须（MUST）引用它所依据构建的那个隐患集合版本。该集合至少必须（MUST）钉定：
  - **时间戳**——来自打了标签提交的 `SOURCE_DATE_EPOCH`（RB-4b）；任何发出的归档
    里都没有 mtime；
  - **构建路径**——`--remap-path-prefix` 到一个固定的 `/build` 根，从而没有绝对
    路径、`$HOME` 或用户名被嵌入调试信息或 panic 字符串；
  - **并行性与顺序**——codegen-unit 顺序、链接顺序、符号表顺序、归档成员顺序，以及
    任何抵达输出的哈希表迭代顺序，都必须（MUST）被做成确定性的（固定或排序）；
  - **`-C metadata` / `-C extra-filename` 的派生**——从被钉定输入确定性地派生，
    绝不从一个随宿主变化的值派生；
  - **locale/编码**——`LC_ALL=C`；
  - **调试信息与符号**——确定性的，或被剥除；若保留，则确定性；
  - **随机化布局与种子**——`-Z randomize-layout` 关闭；任何以 RNG 播种的 codegen
    被钉定；
  - **归档/打包的封帧**——一个固定编解码器在一个固定级别上，容器元数据里没有文件名、
    时间戳或 uid/gid（ID-4d 规范容器规则，用于软件打包）。

  第 8 部分那处未钉定解码隐患的类比（ID-4d 的 §10 注）在此适用，并被点名、而非藏起：
  **依赖 LLVM 版本的 codegen 与依赖宿主的 `cfg`/特性统一**（在 RB-5a 中已承认）只在
  *截至被钉定工具链与被钉定特性解析之时*才是可复现的；每一次工具链升版都是一项全新的
  确定性审计义务（§10.7），而非免费搭车。
- **RB-6a（产物是内容寻址的；`H_build` 是它唯一的名字）。「[规范性]」** 发布产物以
  `H_build = BLAKE2s(artifact)`（套件哈希，第 0 部分）寻址。`H_build` 是该构建唯一的
  权威名字；一个人类可读的版本字符串（`v1.2.3`）是一个便利标签，不得（MUST NOT）被
  用来替代 `H_build` 而受信任（ID-2「哈希是唯一的名字」规则）。新鲜度——客户端*应该*
  运行*哪个*版本——是一个单独的性质，由 RB-8a 携带，而非由版本字符串携带。
- **RB-6b（`H_build` 是逐目标的；一致是在一个 triple 之内定义的）。「[规范性]」** 一个
  发布从*同一*源码，逐目标地复现出*不同*的字节（`aarch64-linux-android`、
  `x86_64-unknown-linux-gnu`、`armv7-…`、……），所以 `H_build` 是
  **（打了标签的源码、清单、目标 triple）** 的一个函数。清单必须（MUST）钉定目标
  triple；一致（RB-9）**只在一个固定 triple 之内**定义；并且 RB-7/RB-15 必须（MUST）
  只比对同 triple 的 `H_build`。一个把自己 triple 的哈希与一个不同 triple 的已发布
  哈希相比对的客户端，不得（MUST NOT）引发一次构建背离异常——那是一个范畴错误，
  而非一次攻击。本部分还确切地钉定了 `H_build` 对每个发货产物（节点二进制文件，以及
  单独地、任何安装器或库）覆盖哪些字节，从而两个重建者哈希的是同一个对象。

## 7. 两方如何认同它们持有同一二进制文件

- **RB-7（一个陌生人的重建并比对流程）。「[规范性]」** 一个*与任何贡献者毫无关系*的
  方为获得一个比特相同的产物并核验它而运行的流程：
  1. 从**任意**镜像取回打了标签的源码与清单（RB-8）；
  2. 对照每个输入的清单 `BLAKE2s` 核验之（RB-3、RB-5）；
  3. 为该目标 triple 运行密封构建（RB-4、RB-6b）；
  4. 计算 `H_build`；
  5. 按 `BLAKE2s` 相等去比对已发布哈希（RB-14）以及任意对端的同 triple 哈希。

  相等的 `H_build` 是同一二进制文件的证明；不等则是它们不同的证明，且必须（MUST）
  作为一次**构建背离（build divergence）**（RB-15）浮现出来，绝不悄无声息地和解。
  这场争议可由任何人解决，无需向权威申诉：重建，看公开源码产出什么（ID-5a 裁决者，
  用于软件）。这就是那条 4.2「完成」判据：两方在不同机器上，经由一个未点名任何受
  信任单例的流程，从打了标签的源码产出哈希相同的产物。
- **RB-7a（一个不复现的发布被拒绝，而非被打补丁糊弄过去）。「[规范性]」** 一个其
  `H_build` 无法从其所述清单复现出来的已发布产物，按定义就不是那段源码的构建：一个
  *能够*重建的合规核验者必须（MUST）拒绝它，并应当（SHOULD）把该差异作为一处构建异常
  （RB-15）gossip 出去。「它在维护者的机器上构建得出，但别处都不行」是一次可复现性
  失败——一处缺陷——而非一个可接受的状态（ID-5b 规则，用于软件）。
- **RB-7b（无法重建的客户端——那个模态用户）。「[规范性]」** 几乎每一个真实用户都在
  一台没有工具链、没有磁盘、也没有带宽去编译依赖树的手机上运行客户端；它*无法*执行
  RB-1 的操作 (b)。这样一个客户端必须（MUST）把它运行的每一个二进制文件跟踪为
  **`reproduced-by-others-unverified`**，直到它（或一个它随后与之 `H_build` 相匹配的
  对端）完成重建；必须（MUST）依 RB-10 规则把佐证当作一个**独立验证过的**复现者的
  计数（绝不是一个原始的证明堆积计数）；并且本部分直白地陈述：**对不重建的客户端
  而言，构建信任并不从复现流出——它归约为按数量佐证，即 OP-2**，恰如第 8 部分里
  不重建的映射客户端的映射信任向 OP-2 归约（§10，ID-5b/§10）。客户端必须（MUST）把
  这一状态浮现出来；它不得（MUST NOT）把一个未重建的二进制文件呈现得仿佛用户已经
  核验过它。

## 8. 清单、一致，以及新鲜度

- **RB-8（清单是复现配方）。「[规范性]」** 每一个发布都必须（MUST）发货一个**清单
  （manifest）**：源码提交/标签、被钉定的工具链哈希（RB-3）、每个依赖的内容哈希
  （RB-5）、固定环境（RB-4b）、目标 triple（RB-6b）、`SOURCE_DATE_EPOCH`（已派生，
  RB-4b）、隐患集合版本（RB-6），以及预期的 `H_build`。清单——而非某台服务器、某个人
  ——定义了构建（ID-3 清单，用于软件）。
- **RB-8a（清单是规范的、内容寻址的；新鲜度是一个可核验字段）。「[规范性]」** 清单
  必须（MUST）有一个**规范序列化**（重用第 2 部分的规范 CBOR 配置，GR-21..GR-30），
  并且其自身由 `manifest-hash = BLAKE2s(canonical manifest)` 内容寻址；否则两个诚实
  方会对同一份配方产出不同的 manifest-hash，而日志佐证（RB-14）便会在一处格式差异上
  分裂——GR-21 的教训未学到。清单必须（MUST）携带一个**单调发布索引**，与那个派生的
  提交者日期绑在一起，并且透明性日志叶子（RB-13）必须（MUST）保全那个排序，从而
  *新近度（recency）*是该产物的一个可核验性质。这弥合了与 4.1 之间那道 4.1 日后无法
  弥合的接缝缺口（清单 schema 是一个 4.2 产物）：见 RB-9a。
- **RB-9（一致即哈希相等，仅此而已）。「[规范性]」** 两方持有同一二进制文件**当且
  仅当**它们同 triple 的 `H_build` 相等（RB-6b）。比对是一次 32 字节检查；它不需要
  签名者，不需要法定人数，不需要权威（ID-5 规则，用于软件）。
- **RB-9a（可复现性证明二进制匹配源码，而非源码是当前的——新鲜度残余）。
  「[规范性]」** `H_build` 认证的是*那些字节匹配该源码*；它对*哪一份源码才是要运行
  的那一份*只字未言。一次**可复现降级攻击（reproducible-downgrade attack）**——给
  一个客户端喂一个带着已知漏洞的旧标签，它完美地复现并通过上面每一项 RB 检查——
  **只**能被一条新鲜度规则击败。本部分为那条规则提供可核验输入（RB-8a 的单调发布
  索引 + 派生日期，在日志中被排序，RB-13）；使用它的那条*采纳策略*（拒绝一个低于已见
  的索引；对过期发出警告）是条目 4.1，且是客户端本地的。残余：仅凭可复现性并不击败
  降级；本部分所强制的那个清单字段才是让 4.1 *有可能*击败它之物（ID-4 epoch，用于
  发布）。

## 9. 与更新治理的合并接缝（OP-8 / 条目 4.1）

发布签名者与映射的根发布者看起来像是同一套机制。**立场，映照第 8 部分的 §9：在信任上
保持它们分离，即便它们共用工具。**

- **RB-10（一个证明是一则复现声称，按独立再复现加权，而非按谁发出它加权）。
  「[规范性]」** 一个构建**证明（attestation）**是一句陈述 *「我为 triple T 重建了
  清单 M 并得到了 `H_build`」*——一份**复现报告**，而非一个授权。它的权重来自于它是
  **可被独立核验的**（任何人重跑 RB-7 并予以确认或反驳），而非来自证明者的身份：一个
  以化名签名的证明与一个未签名的证明，一旦某个第三方复现了该声称便携带**相同**的权重；
  签名只*定位*该声称（RB-2）。佐证必须（MUST）确切遵循第 2 部分的纪律：**只计数独立
  验证过的复现，绝不计数一个原始的证明数目**（GR-20 / PS-10「只计已验证，绝不计原始」
  规则）。并且本部分承认 GR-19a 已经证明之事：**复现者的独立性无法单凭证明来核验**
  ——你无法把 10 000 个复现者与一个戴着 10 000 副面具的方区分开来——所以一个复现者
  计数是一个*弱*信号，归约为 OP-2，而那个*强*信号是客户端自己的重建（RB-7）。一个其
  证明的接受取决于证明者身份、或其中一个未验证证明的原始计数就佐证一个构建的设计，
  是不合规的（RB-1，并且它正是 RB-10 存在所要禁止的那个可被 sybil 投票的多数权威）。
- **RB-10a（规范证明格式，按复现者去重）。「[规范性]」** 证明要跨越线路（RB-14）并
  喂给一个计数（RB-10），所以它们必须（MUST）有一个规范编码（重用规范 CBOR，
  GR-21..GR-30），否则两个诚实证明者会产出互不匹配的字节而计数便会坏掉。证明必须
  （MUST）按 `(复现身份, M, triple, H_build)` 去重，并且权重是**逐独立复现者的，绝不
  是逐证明字节串的**，从而一个对手无法通过铸造一个声称的字节相异变体（格式填塞，
  format-stuffing）来虚增佐证。
- **RB-11（工具链必须确定性可用地构建；存在一个跨宿主测试向量）。「[规范性]」**
  因为被钉定的工具链本身就可能嵌入非确定性（并行 codegen、`OUT_DIR`、元数据里的
  宿主 triple），本部分必须（MUST）钉定那些让它跨宿主产出相同输出的标志与模式
  （RB-6），并且必须（MUST）存在一个**跨宿主构建测试向量**（清单 → 一个固定 triple
  的预期 `H_build`），使得第二台机器能证明它复现出完全相同的产物（ID-4d 映射测试向量
  规则；关联到 roadmap 3.2 的一致性测试框架）。这是第 9 部分 RI-1b 的 RB 类比：*一次
  通过的功能测试证明的是二进制文件能运行，而非它是比特相同的*——可复现性由重建并比对
  检查，绝不从「它编译通过了」被假定。
- **RB-12（贡献者是化名的；信任只经由可复现性流动）。「[规范性]」** ScrambNet 没有
  **身份绑定的签名密钥**，也没有受信任的作者身份。对一个二进制文件的信任必须（MUST）
  **完全**派生自 (a) 源码是公开且可审阅的（I-1），以及 (b) 二进制文件从那段源码复现
  得出（RB-7）——**绝不**派生自*谁*写了、提交了、打了标签或签了名。一个需要一个
  受信任的作者、维护者或签名者身份才能接受一个构建的步骤，在 RB-1 与项目的化名规则
  二者之下都是不合规的。这就是本部分核心张力的解法：*作者按构造是不受信任的；二进制
  文件按复现是受信任的。*
- **RB-12a（化名密钥是干什么用的——以及它们所依赖的前提条件）。** 一个贡献者密钥，
  倘若被用到的话，认证的是*一个化名的连续性*并*定位*工作（这次提交、这份证明，来自
  同一只化名之手）——一个用于 gossip 以及用于 4.1 定位符角色的便利（RB-2），绝非
  构建信任的根。丢失、轮换或替换这样一个密钥，不得（MUST NOT）使任何仍然复现得出的
  二进制文件失效。一个被攻陷密钥的持有者，无法发出一个能**在一个诚实审阅者加一个诚实
  复现者面前存活下来**的恶意但可复现的二进制文件——然而那层保护是*它们的存在*，而非
  密钥：缺了一个对源码的诚实审阅者（I-1）与一个客户端够得着的诚实复现者（RB-7/RB-10），
  那个被攻陷的密钥*就能*把一个恶意二进制文件发给一个既不审阅也不重建的客户端
  （RB-7b）。所以那层保护归约到 I-1（审阅）与 OP-2（诚实复现者的可达性）；它不是密钥的
  一个无条件性质。（这把前提条件显式陈述出来，从而那个声称不是循环论证。）
- **RB-12b（可复现性证明二进制匹配源码，对源码诚实性只字未言）。** 可复现性与审阅是
  **正交的两个轴**。可复现性证明二进制文件匹配源码；它对源码是否诚实只字未言。化名
  （RB-12）移除了「一个受信任的作者为源码担保」，所以源码诚实性系于**公开审阅
  （I-1）**，别无其他。本部分直白地陈述这一点，从而没有读者会把「可复现」错当成
  「安全」或「已审阅」：一个带后门源码的忠实复现构建，是一个后门的忠实复现（§10、
  OP-10）。
- **RB-13（哈希与清单被发布到一个无需许可的日志，按发布索引排序）。** 发布
  `(triple, H_build, manifest-hash, release-index, committer-date)` 元组应当（SHOULD）
  被公告到用于映射的同一批无需许可的仅追加透明性日志（ID-6/ID-7），保全 RB-8a 的
  排序，从而构建公告被加盖时间戳、且含混其辞可被检测，**没有任何特权追加者**（ID-7）。
  日志并不*册封*一个构建——那由复现来做（RB-7）——它使「向不同的人展示不同的二进制
  文件」变得可检测，并给新鲜度（RB-9a）一个被见证的顺序。依 RB-2a，日志*构造*是与映射
  共用的；而那些*实例/集合*应当（SHOULD）保持独立（ID-7b「多个日志，没有一个规范
  日志」），从而那两个可用性域不会塌缩成一个承重的运营者。
- **RB-14（gossip 构建元组；检测分裂视图）。「[规范性]」** 客户端与重建者应当
  （SHOULD）在 GR-8 来源混合之下经由 GR-6 去 gossip `(triple, H_build, manifest-hash,
  release-index)`，并索要透明性日志一致性证明，从而一个向 Alice 提供二进制文件 X、
  向 Bob 提供二进制文件 Y（同一 triple，相同或冲突的索引）的对手，会被任意一个同时
  持有二者的方逮到（ID-7a 含混其辞防御，用于构建）。一个把构建追加设门槛在一个签名者
  集合之后的日志是不合规的（RB-2a/ID-7）。
- **RB-15（构建异常被 gossip，而非被压制）。「[规范性]」** 有四个事件是构建异常，
  每个核验者在检测到时都必须（MUST）gossip，只比对同 triple 的哈希（RB-6b）：(a) 一个
  无法从其清单复现的 `H_build`（RB-7a）；(b) 一个在构建公告上呈现不一致根的透明性
  日志（已证实的含混其辞）；(c) 一个针对独立复现者的持续同 triple `H_build` 背离；
  (d) 一次**发布索引回退**——一个标签以一个低于已为该发布线见证过的索引被呈现（降级
  签名，RB-9a）。一个核验者不得（MUST NOT）为了让一个发布看起来健康而压制一个异常
  （ID-10 免疫信号规则，用于构建）。

## 10. 本部分未解决之事（已声明的残余）

本部分使两个*都重建*的方可证明地取得一致、或可证明地检测到它们不同，并且它把信任从
*谁构建了它*移到*它是否重建得出*——一次真实且巨大的归约，对一个化名项目而言是正确的
那一次。它**并不**使二进制文件*安全*。那些缺口是真实的，且被声明、而非被抹平：

- **§10.1 —— 一个被钉定依赖里的后门被忠实复现，而非被逮住。** 如果一个被 vendored
  的 crate 含有敌意代码，每一个重建者都得到那个完全相同的恶意二进制文件，而 RB-7
  *确认*了这次匹配——复现恰恰如设计所意那样工作着，并且对这份恶意是盲的。二进制文件
  诚实地反映了被诚实地加了后门的源码。唯一的防御是**公开审阅（I-1）、审计（RB-16），
  以及最小化依赖面（RB-5/RB-17）**——那些*界定*该面的人类过程，没有一个是无权威的
  密码学检查。**这是首要残余，它没有不受信任的替代物，并且它是本项目那个反复出现的
  问题戴着第四副面具——OP-10。** 价值主张恰恰在此处是诚实的：可复现性**并不**防御
  那个最可能的现实世界攻击，而且它从未打算防御——但它改变了*需要哪一类*攻击。没有它，
  一个攻击者毒化**一个目标的一个二进制文件**，不可见且不可归因。有了它，一个恶意
  二进制文件必须追溯到**人人可审阅**、且**对每个人都复现相同**的**公开源码**——把攻击
  从「毒化二进制文件」（不可见、逐目标）逼成「毒化公开源码或一个公开依赖」（可审阅、
  普适、最大程度地暴露给那一个诚实审阅者）。那场转换就是本部分的价值；逮住被毒化的
  源码是 OP-10 与 I-1，而非可复现性。
- **§10.2 —— 一个可复现地错误编译的被攻陷工具链。** 一个带后门的 `rustc`/LLVM 能把
  源码里没有的行为确定性地插入进去，从而每一个重建者都复现出那个完全相同的坏二进制
  文件，而 `H_build` 相等成立。钉定（RB-3）使每个人共享一个编译器，并使*替换*它变得
  可检测；它并不使那个被钉定的编译器变得诚实。**没有不受信任的替代物**，除非是从源码
  自举或多样化双重编译，而本部分把它们点名为未来工作（RB-3b），而非一项当前要求。
- **§10.3 —— Trusting-trust（Thompson）。** §10.2 的一般情形：一个编译器既加后门，
  *又*把那个后门传播进它所构建的编译器里。钉定编译器字节并不打破那个循环；它保证的
  是每个人都在*同一个*循环之内。已声明，而非已解决。（这正是为什么 RB-18 说
  「每一个输出字节都追溯到一个*被钉定*的输入」——来源——而**明确不**说「追溯到一个
  诚实的输入」：一个被哈希、被钉定、带后门的编译器满足可追溯性，却仍然是恶意的。）
- **§10.4 —— 可复现 ≠ 安全；可复现 ≠ 已审阅。** 一个看起来诚实、却微妙地出错之源码
  的完美可复现构建，是完美可复现的。化名（RB-12）意味着没有受信任的作者为源码担保，
  所以源码诚实性完全系于公开审阅（I-1）；可复现性与审阅是正交的（RB-12b）。
- **§10.5 —— 按数量佐证归约为 OP-2；那个不重建的客户端是模态用户。** 「N 个独立
  重建者得到了 `H_build`」的强度只与那 N 个的*独立性*相当（RB-10、GR-19a）。一次
  诚实的再复现以确定性反驳一个虚假声称（比映射情形更强，因为源码是确定性的），但一个
  **无法重建**的客户端（RB-7b——那台手机，即几乎每一个用户）倚仗那个证明计数，而那是
  一个可被 sybil 投票的法定人数：一个对手为一个坏的 `H_build` 铸造化名证明，而一个
  被**日蚀（eclipse）**的客户端只看到对手的证明、从不遇到一个诚实复现者。所以对那个
  不重建或被日蚀的客户端而言，「没有权威」意味着「信任那个已验证复现者法定人数」，
  而那只在 **OP-2** 成立的限度内成立。本部分把构建权威问题对不重建者**归约**到
  OP-2；它并不消解它——与第 8 部分收尾时相同的那次归约（ID-1 → OP-2）。
- **§10.6 —— 裁决者是活性（liveness）受界的；托管（escrow）必须被复制，否则它就是
  一个单例。** 重建并比对是那个无权威的裁决者，**只在被钉定的输入仍可取回之时**。
  工具链二进制文件与整棵 crate 树体量庞大且易朽：一个**被撤回的 crate**或一个**被
  取消发布的工具链发布**会使 `rebuild(manifest)` 无法执行，那时那一个受信任的操作便
  没了——对恰恰最需要它的那些取证争议（「v1.2 被加后门了吗？」）而言最为糟糕。一个
  合规的部署应当（SHOULD）把被钉定的输入字节托管在一个内容寻址的存储里，并**跨与构建
  相同的那套无需许可镜像集合复制**；一个单副本托管是内容寻址的（所以它不能*撒谎*），
  但它是一个**活性单例**（它能*消失*），而 I-3 涵盖活性。缺了复制，RB-7 被声明为
  **活性受界**，而非无条件的（ID-5a 活性残余，用于构建）。
- **§10.7 —— 面对工具链流变，确定性是一个移动的靶子。** 新的 `rustc`/LLVM 版本引入
  新的非确定性来源（新的并行 pass、新的元数据、新的 `cfg` 行为）。RB-6 的隐患集合是
  **当前的**，而非封闭的；一个被钉定的工具链*按其被钉定*是可复现的，但每一次工具链
  升版都是一项全新的确定性审计义务，并且清单记录它依据哪个隐患集合版本构建（RB-6、
  RB-8）。「复现一次」不意味着「永远复现」。
- **§10.8 —— 首次构建 TOFU：一个恶意的首个二进制文件对自己的复现撒谎。** 一个崭新
  用户的*第一个*客户端二进制文件在它被用来自举之前无法被复现（你需要一个能工作的
  客户端去取回源码、工具链，并触及日志与对端）。第一个二进制文件按首次使用即信任被
  采纳，恰如第 8 部分的第一个映射那样（ID-8）——而且更糟：一个被攻陷的首个二进制
  文件此后拥有用户的整套复现与 gossip 装置，所以它能**对自己的复现撒谎**（「我重建了
  自己；`H_build` 匹配」）。因此一个客户端无法诚实地核验*它自己*的复现；首个二进制
  文件的信任系于一个**带外的独立复现者**——一台用户信任程度高于被测二进制文件的
  不同机器/工具链。这是那条「trusting-trust」/被攻陷宿主的边界（§10.9）；它是一个
  已声明的残余，在此陈述、而非被「超出范围」悄无声息地吞掉。
- **§10.9 —— 本部分甚至不去尝试之事。** 用户机器的运行期被攻陷；一个在被攻陷宿主上
  *由用户自己对诚实源码所作的恶意构建*（复现确认了那次匹配；宿主仍然拥有那个进程）；
  以及产物边界之上的一切——安装，以及更新*采纳*（运行哪个构建、何时运行），那是条目
  4.1。本部分只关乎比特相同的产物；它把这些点名为超出范围，而非已解决。

那个诚实的总结：可复现构建把信任从*谁构建了它*移到*它是否重建得出*——真实且巨大。
但它们对源码是否诚实**沉默**（§10.1、§10.4），对一个可复现的编译器/依赖后门
**盲目**（§10.1、§10.2、§10.3），作为一个裁决者是**活性受界的**（§10.6），对那个
不重建或被日蚀的客户端**归约为 OP-2**（§10.5）——那个模态用户（RB-7b）——并且在
首个二进制文件上是 **TOFU**（§10.8）。这些是拒绝一个发布权威的代价。正确的应对是把
它们界定住——最小化并审计那个受信任的计算基座、复制托管、鼓励独立重建、携带那个
新鲜度索引——并把它们陈述出来，而非隐藏它们。

## 11. 界定残余的供应链卫生

- **RB-16（依赖与工具链审计是强制的、在范围之内的）。** 因为复现看不见一个每个
  重建者都忠实复现的后门（§10.1），本部分必须（MUST）要求对依赖集合与工具链有一份
  已提交、可审阅的审计轨迹（`cargo-vet`/`cargo-audit` 风格的记录，按内容钉定），把它
  当作**审阅证据（I-1），而非当作权威**。审计缩减那个 §10.1 攻击面；它并不移除它，
  而本部分如此说明。
- **RB-17（最小化那个受信任的计算基座）。** 本部分应当（SHOULD）要求主动收缩那个
  必须被信任并审计之物：更少的依赖（RB-5），更少的 `build.rs`/proc-macro（RB-5b），
  一个更小的工具链面（RB-3a），在可行之处用 `#![forbid(unsafe_code)]`——因为那个
  受信任计算基座的每一个要素都是审计必须覆盖、而复现无法覆盖的一个 §10.1 残余。
  诚实的一点：「最小」不是「小」——一个真实的 async + 密码学节点（一个 async 运行时、
  一套 Sphinx/X25519 栈、CBOR，……）会拖进*数百*个传递 crate，许多还带构建脚本，
  所以那个 §10.1 的依赖后门残余不是一个边角情形，而是那个**预期中的**攻击面。那就是
  OP-10 那个诚实的措辞。
- **RB-18（整条链条要么被钉定、要么就是未被钉定——而被钉定意味着来源，不是诚实）。
  「[规范性]」** 任何地方的一个单一未钉定输入——一个未被哈希的工具链组件、一个浮动
  依赖、一个读取宿主的 `build.rs`、一个按标签取回的容器基础镜像——会使整个产物的
  可复现性声称作废，因为那一个输入重新把一台服务器或一个宿主引入成一个受信任方
  （RB-1）。清单必须（MUST）是**完整的**：如果一个输出字节无法被追溯到一个*被钉定*
  的输入，那个构建就是不合规的（ID-4c 规则，用于软件）。**这是一个确定性/来源声称，
  而非一个信任声称：** 一个被钉定的输入可以是恶意的（§10.1、§10.2、§10.3）；钉定
  使那份恶意对每个人都相同，并使任何*相对于一个诚实输入的背离*可检测——它并**不**
  使那个输入变得诚实。「被钉定」从不意味着「安全」。

## 12. 此处引入的需求

- **RB-1 / RB-2 / RB-2a** —— 没有发布权威，复现是裁决者；签名只定位，绝不授权；与
  映射共用工具，绝不共用权威。
- **RB-3 / RB-3a / RB-3b** —— 工具链跨整个编译面按内容钉定；那个被钉定的编译器是一个
  已声明的「trusting-trust」残余（来源，不是诚实）。
- **RB-4 / RB-4a / RB-4b** —— 密封、离线、无环境污染的构建；没有构建期取回；一个固定
  环境，其 `SOURCE_DATE_EPOCH` 从打了标签的提交**派生**得出。
- **RB-5 / RB-5a / RB-5b** —— 最小化、已 vendored、按内容钉定的依赖树；锁文件必要但
  不充分；构建脚本与 proc-macro 是被沙箱化的受信任计算。
- **RB-6 / RB-6a / RB-6b** —— 规范的、按工具链版本化的非确定性隐患集合；`H_build` 是
  唯一的名字；`H_build` 是逐（源码、清单、目标 triple）的，且一致是在一个 triple
  之内的。
- **RB-7 / RB-7a / RB-7b** —— 陌生人的重建并比对；拒绝不可复现者；那个不重建的模态
  用户跟踪 `reproduced-by-others-unverified` 并归约为 OP-2。
- **RB-8 / RB-8a / RB-9 / RB-9a** —— 清单是配方，规范且内容寻址，携带一个单调发布
  索引；一致是同 triple 的哈希相等；新鲜度残余（可复现降级）连同 4.1 所需要的那个
  清单字段。
- **RB-10 / RB-10a** —— 一个证明是一则复现声称，按独立再复现加权（只计已验证，绝不计
  原始；独立性是 OP-2）；规范格式，逐复现者去重。
- **RB-11 / RB-12 / RB-12a / RB-12b** —— 跨宿主构建测试向量；信任只经由可复现性流动；
  化名密钥定位，绝不作信任之根（前提条件被显式陈述，非循环论证）；可复现性 ⊥ 审阅。
- **RB-13 / RB-14 / RB-15** —— 按发布索引排序的、构建元组的无需许可日志；gossip +
  分裂视图检测；四个强制异常，包括那个降级签名。
- **RB-16 / RB-17 / RB-18** —— 作为审阅证据的强制审计；最小化那个 TCB（它仍然很大）；
  整条链条被钉定，其中被钉定是来源，不是诚实。

RB-1 与 RB-7 是承重的两条：没有权威，以及复现是裁决者。二者都是有界的，而非绝对的
—— 对不重建的客户端而言 RB-1 归约到 OP-2（§10.5，那个模态用户），而 RB-7 是活性
受界的（§10.6）。那个最尖锐的残余，被陈述、而非被隐藏，是 §10.1：**可复现性不逮住
一个带后门的依赖，而那是最可能的真实攻击——它把攻击逼进公开、可审阅、普适的源码，
那正是要点所在，而在那里逮住它是 OP-10，不是本部分。** 打破本部分，靠点名一个需要
受信任方的构建步骤、一个无法从其清单重建的已发布产物、一个 RB-6 漏掉的确定性隐患、
一条签名绕过 RB-2 把授权偷运回来的路径，或者一条让那个不重建的客户端被留着信任一个
并非 OP-2 的多数的路径。那就是邀请，以第 8 部分的那种声音。
